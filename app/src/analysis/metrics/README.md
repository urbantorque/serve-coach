# Metrics layer (engine-core)

Every value is a `MetricValue` with an honesty label (measured, estimated, player-entered, experimental, unavailable), a reason code on every downgrade or unavailable value, and, for numbers, a 95% interval built from the METRICS §1.2 components (σ_r, σ_leak, σ_s + σ_p).

| File | What it does |
| --- | --- |
| `catalogue.ts` | Runtime copy of `docs/specs/metrics.json` (units, target statuses, views, unlock hints, plausibility bounds; `catalogue.test.ts` checks drift) and the engine-side **validation levels** from the latest synthetic run. Status = min(target, validation ceiling in the session's condition class). |
| `status.ts` | `finalizeMetric` (ceiling → night cap → per-value downgrades) and `unavailable` (reason text + unlock hint). Wrong view → `NEEDS_SIDE_VIEW` / `NEEDS_REAR_VIEW`. |
| `perServe.ts` | `CONTACT_DEPENDENT_IDS`: the values that depend on the contact time (directly, or through the trophy window and the landing search); when the contact timing signals disagreed (serve/analyse.ts, D2 addendum) they are experimental or withheld (`CONTACT_NOT_FOUND`), and their basis names the signals. Formulas of §3 per serve: toss height (depth-corrected), toss forward/lateral, drop (physics), contact height/forward, rhythm, trophy pause, leg drive, drive time, loading depth, deep-bend flag, shoulder tilt (φ kept internal, never displayed), rear knee band, shoulder over shoulder, landing distance, launch speed (D4 prerequisites), plausibility bounds. |
| `session.ts` | Per-stratum aggregation: centres, noise-corrected spreads with censoring and "at least", provisional labels, provisional bands with hysteresis, F3/F4/F12 trigger statistics, repeatability, fatigue flag; every metric id present with a status. |
| `repeatability.ts` | The experimental 0–100 index and the representative serve. |
| `precision.ts` | The ONE display precision (METRICS §4.9): 0.5 cm spreads, 1 cm heights, 2-decimal ratios, 10 ms durations, 5 ms timing spreads, and 5 cm steps when the 95% interval's half-width is 10 cm or more. The engine's headline and the UI's `formatMetric` both use it, so a quantity reads the same on every screen. |
| `headline.ts` | The session headline sentence (METRICS §4.1 headline rule), shared by the engine (stored `SessionStats.headline`) and the UI (`ui/format/sessionValues.ts` rebuilds it from stored values). |
| `setup.ts` | The set-up key `orientation | distance class | serving spot` (METRICS §1.6): distance classes from D (close < 6.75 m, standard to 8.25 m, far), `sameSetup` (unknown spot and older sessions match), words. Written on every `StratumKey.setup` and `SessionStats.setupKey`; coaching and the UI never pool or compare across set-ups. |

**Capture quality** (DECISIONS D2 addendum, 2026-09-28) goes through `finalizeMetric` like every value: target measured, validation V0, so `experimental` (`VALIDATION_PENDING`), with the basis "Automatic check, experimental (tested on simulated footage only)". It is a data-quality gate, so the UI shows it even with experimental metrics off.

Current validation levels (synthetic, 122 clips): V1 for serve count, contact height (D1 distances ≥ 6 m), toss drop, rhythm (≥ 45 fps), leg drive, loading depth and the four spreads; everything else V0 (experimental) with the reasons in `catalogue.ts` and `validation/results/metrics/SUMMARY.md`. V1 needs the method-only variant (truth landmarks plus noise) to pass at D1 as well as the app pipeline (finding 41, 28 September): toss height passes through the app pipeline only because MediaPipe's ~3% high head reading cancels the depth prior's over-correction, so it stays V0 (`VALIDATION_PENDING`) until a real-footage (V2) check. Its spread keeps V1, so its relative use (`statusIfLevel`) is still estimated.

Light (METRICS §1.3): the condition class comes from the player's answer (no answer: `unknown`, nothing validated), lowered by the pixels (`quality/light.ts`, measured on the sparse pass): mains flicker ≥ 3% makes it `flicker` (speed blocked, `FLICKER`), a near-black sky over a lit court turns a daylight answer into `night-lights`. Pixels never raise it.

Per-serve scale (E1): the time base is a clip property (the container, else the median toss fall over the session, `engine.ts` `timeBaseOf`). A serve whose own toss falls more than 10% (and 3σ) off the others is flagged (`serveScaleOff`, `SCALE_INCONSISTENT` on its body-scaled values), never rescaled; a serve with fewer than 5 upright frames takes its standing height from the serves at the same floor row (`sessionBodyHeight`), never a median over both court sides.

Imports with a mount answer (METRICS §1.1 item 3a): `assumedLevelHeight` in `perServe.ts` propagates the pitch and roll priors into the shared σ of toss and contact height and keeps contact height `estimated` (`TILT_UNKNOWN`) only while `√(p95² + (1.96·σ_tilt)²) ≤ 0.05` of standing height (`ASSUMED_LEVEL_HEIGHT_BUDGET` in `catalogue.ts`: the larger of the app-pipeline and method-only p95 at D1, 0.056 for toss height, which is V0 anyway, and 0.039 for contact height); otherwise, and for forward positions and angles, `PITCH_UNKNOWN`. The engine's standing-body roll check (> 3°) turns the answer back into an unknown pitch.

Unknown phone pitch (imports, no motion access): per METRICS §1.1 item 3, absolute heights and positions are capped at experimental (`PITCH_UNKNOWN`), but spreads keep their status. `finalizeMetric` records the status a value would have with a known pitch in `MetricValue.statusIfLevel`; the spread summaries (`session.ts` `collect(…, forSpread)`) and coaching's spread series (`coaching/series.ts` `forSpread`) use it, and the report shows each toss peak against the middle one instead of absolute heights (integration change).
